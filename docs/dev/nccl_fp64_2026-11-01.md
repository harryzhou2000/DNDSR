# NCCL and FP64 tensor-core preliminary complement

Date:2026-11-01 (Asia/Taipei). Status: implementation/validation in progress.

The NCCL provider (enabled by default for CUDA, explicitly disableable) uses
existing row/payload plans, prepared device
scratch and stream-enqueued transfer/unpack. MPI remains the default and setup
control plane. Public C++/Python selection and the caller contract are described
in [NCCL transfers](../architecture/NCCLTransfer.md).

Jacobi has an explicit ordinary-FP64 or FP64-MMA selection. The small shared
Algebra adapter uses double-input/double-accumulator8x8x4 MMA; CFV handles padded
tails, periodic vectors, boundary terms and the existing strided U/URec views.
WBAP remains ordinary FP64. See [device reconstruction](../architecture/DeviceReconstruction.md).

Initial development tests passed the CPU row-transfer np1/2/4/8 matrix and five
GPU CTest registrations each at np1 and np2: NCCL row transfers plus ordinary,
tensor, NCCL and combined CFV modes. The first expanded NCCL suite reports
5 cases/1220 assertions per rank; CFV reports5 cases/349314 assertions at np1
and5 cases/178195 or171165 assertions at np2. These development checkpoints
precede the final source rebuild and are not final phase acceptance.

Inspection of the compiled sm80 tensor-core object finds1 DMMA,0 HMMA,
15 DFMA,3 DMUL and3 DADD instructions. This establishes an actual FP64 MMA path,
not a speedup. Fresh Python rebuild/install, full regressions, sanitizer gates
and matched real-wrapper timing results remain pending.

Graph capture, graph pools and the optional schedule checker are outside this
phase. New providers do not infer cross-stream dependencies. No new top-level
library, Torch dependency, Geom physical format or solver frontend was added.
